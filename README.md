# Triage : Conversational Analytics for Support Data

Ask a Natural Language query about any dataset and get back a
grounded answer: a short explanation, a computed number, and a chart each
filled in only when it applies, never invented.

## How it works

Every question goes through the same four-stage pipeline:

| Stage | What happens |
|---|---|
| **1. Classify** | An NLP classifier reads the question and decides which components it needs (numeric, chart, prediction, and/or lookup). No LLM call for this step. |
| **2. Route** | Based on the classification, the question is sent to the appropriate handler direct computation, semantic retrieval, or chart aggregation. |
| **3. Compute** | The answer is produced deterministically: a real pandas aggregation, a vector search over ticket text, or a trained scikit learn model. Nothing here is generated by an LLM. |
| **4. Synthesize** | An LLM (via Groq) writes the final explanation, but only from the facts already computed in stage 3  it is explicitly told not to invent numbers, so the text can't contradict the data. |

The result: **text is always returned**, and **numeric**/**chart** are added only
when the question calls for them. All three render in a fixed three-tile layout
that never reshuffles between queries.

## Why intent classification is NLP, not an LLM call

Early versions of this project routed every question through an LLM to decide
what kind of answer it needed. That's unnecessary: the intent space is small
and closed (does this question need a number? a chart? a prediction? does it
need to read ticket text?), which is exactly the kind of problem classical NLP
pattern matching solves well and solves it with zero latency and zero API
cost, instead of burning an LLM call just to make a routing decision.

The classifier (`classify_intent_classical` in `backend/main.py`) matches the
question against a small set of regex patterns per intent (aggregation
language like "how many"/"average", chart language like "by channel"/"trend",
prediction language like "predict"/"estimate", and content-lookup language
like "what issues"/"describe"). This cut LLM calls per query from up to three
down to at most two.

## Why the LLM never computes the answer directly

The LLM is used for exactly two things: **generating the instructions for how
to compute an answer** (a pandas expression, a chart spec, a set of retrieval
attributes), and **writing the final explanation grounded in the result**. It
never states a number itself. This distinction matters — if a numeric question
is routed straight through an LLM, it will happily hallucinate a
plausible looking wrong number. Here, the number always comes from pandas
actually running against the real dataframe; the LLM only decides *how* to
look, never *what* it finds.

Retrieval (ChromaDB, with a locally fit TF-IDF embedding — no external model
download required) is used only for the "lookup" intent: semantic questions
over free-text fields like `Ticket Description` and `Resolution`. It is
deliberately **not** used for counts or averages — retrieval returns
similar-looking rows, not all matching rows, so it's the wrong tool for
aggregation and would silently produce incorrect statistics.

## Setup

### 1. Get the dataset



Download the real dataset and drop it in the same location with the same filename: 

https://www.kaggle.com/datasets/suraj520/customer-support-ticket-dataset


The backend inspects the CSV's actual columns at runtime rather than assuming
a fixed schema, so it adapts automatically : including deriving a resolution
duration from the raw timestamp columns when a pre-computed hours column
isn't present.
.

### 2. Backend

\`\`\`bash
cd backend
pip install -r requirements.txt
cp .env.example .env        # then add your GROQ_API_KEY
python train_model.py       # trains model.joblib for the prediction intent
uvicorn main:app --reload --port 8000
\`\`\`

Get a free Groq API key at https://console.groq.com/keys.

### 3. Frontend

No build step : static HTML/CSS/JS.

\`\`\`bash
cd frontend
python3 -m http.server 5500
\`\`\`

Open `http://localhost:5500`. It talks to the backend at `http://localhost:8000`
(CORS is open in `main.py` for local development).

## Known limitations

- **Not production hardened.** The numeric/chart handlers execute an
  LLM-generated pandas expression inside a restricted `eval` (no imports, no
  builtins, blocked keywords). That's reasonable for a local prototype behind
  a firewall, not for an internet facing deployment without further
  sandboxing.
- **Groq API calls have a 20s server side timeout** (and the frontend has a
  30s client side timeout as a second line of defense) to avoid a stalled
  upstream request hanging indefinitely. If you see timeout errors under
  normal conditions, check Groq's status page or your rate limits before
  assuming a bug here.
- **Malformed JSON from the LLM.** There's a regex based extractor to clean up
  occasional formatting issues in the LLM's JSON output, but if you see
  parsing errors regularly, tighten the relevant system prompt in `main.py`
  or add a retry.
- **Retrain before trusting any reported metric.** As above anything
  measured against the placeholder dataset (accuracy, latency, KPI values) is
  not representative of the real data.
